# 短期会话记忆验证记录

验证日期：2026-10-18。

## 实现范围

- `POST /agent/chat` 接收可选 `conversationId`，成功返回 `data.conversationId` 与 `data.reply`。
- 后端生成 UUID，Redis 的 `chat:conversation:<conversationId>` 保存可信 `ownerKey`，从创建起固定 30 分钟有效。
- `@MemoryId` 与 `chatMemoryProvider` 关联独立的 `MessageWindowChatMemory`，窗口为 20 条消息。
- 本地 `ConcurrentHashMap` 跟踪正在使用的请求数，Controller 在 `finally` 中归还计数。
- 定时任务清理空闲且已过期的会话，清空消息内容、移除框架缓存和本地跟踪记录。

## 真实 HTTP 与模型验证

| 场景 | 操作及判定 | 结果 |
| --- | --- | --- |
| 同会话多轮记忆 | 第一轮提供 2 人、预算 100 元、清淡不辣；第二轮携带同一编号要求复述 | 编号一致，正确复述 |
| 同一游客开启新聊天 | 不传编号开启新聊天，询问已提供的人数、预算、口味 | 返回不同编号，说明信息不足 |
| 返回旧聊天 | 使用原编号再次要求复述 | 旧上下文仍保留 |
| 不同游客身份隔离 | 使用两套独立 Cookie；核对 Redis 归属分别匹配各自 Session；双向读取对方编号 | 均为 HTTP 403、`code: 403`、`data: null` |
| 自身记忆未被隔离测试影响 | A 读取自身的 2 人、100 元、清淡不辣；B 读取自身的 3 人、180 元、微辣 | 均正确返回 |
| 过期请求被拒绝 | 新建专用测试会话，验证归属后仅将该 Key 有效期缩为 1 秒；确认 Key 消失后，以同一 Cookie 重试旧编号 | HTTP 404、`code: 404`、`data: null` |

HTTP 404 仅证明入口拒绝旧会话，不直接证明当前运行进程中的记忆对象已经释放。内存状态由下列临时程序检查单独验证。

## 复测提示

1. 启动项目，同一游客的多轮请求保持同一个 Session Cookie；每次回复使用返回的真实编号。
2. 验证身份隔离时使用独立 Cookie 容器，先确认 Session 确实不同；仅新建请求页不能证明身份已切换。
3. 测试过期时只操作本次新建的专用测试会话，确认 Redis Key 已消失，再使用原 Cookie 和旧编号请求；预期 HTTP 404。
4. 验证实际内存清理时，需在受控测试上下文或调试器中同时检查框架记忆和本地计数记录，不能仅以 Redis Key 消失或 HTTP 404 判断已释放内存。
5. 正在回复、故障恢复及竞争场景使用可控等待和同步信号，避免依靠手工同时点击制造时间误差。

## 当前边界与下一步

- 会话当前固定过期，下一步计划实现有效请求的滑动续期；过期或越权编号不能续期或被自动重建。
- 已测身份隔离覆盖游客；两个注册用户的聊天记忆隔离仍需单独验收。
- 使用计数只协调内存清理，未实现同一聊天多条消息的串行处理或明确拒绝。
- 单会话窗口为 20 条消息；全局容量、请求并发上限及消息长度边界仍待完善。
- 消息存在本机内存，进程重启会丢失上下文；尚未支持完整历史归档、跨实例共享记忆或长期画像。
- 真实多轮点餐演示、M1 完整故障恢复与 V1 回归、流式响应及前端体验仍是后续任务。
