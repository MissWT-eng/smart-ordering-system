更新日期：2026-10-26。本记录区分持久自动测试、分阶段临时检查和真实模型联调；各组检查不合并计算为独立业务场景数。

## 已实现的行为

- AI 报价卡允许调整原菜品数量、删除菜品、恢复本地编辑及重新报价。每菜 1～50 份，至少保留一项，最多 20 项；换菜不在首版范围。
- `POST /order-drafts/{draftId}/revisions` 接收修改后的完整 `orderItems`。后端校验本人归属、草稿状态和输入，继承原预算，重新读取在售状态和价格，返回 `{draftId, expireAt, draft}`，不向调用方返回 `ownerKey`。
- Redis Lua 在写入前复核旧草稿归属、剩余有效期、替换状态和新编号冲突，然后保存新草稿并标记旧草稿。旧草稿保留剩余 TTL，不能通过修改或确认继续使用。
- 单实例 `OrderDraftOperationGuard` 协调同一草稿的修改和确认。在途竞争返回忙碌 409；完成后重复确认仍按已有订单返回，数据库的 `orders.draft_id` 唯一索引继续兜底。
- 前端编辑时显示待核价，禁止确认旧金额；成功后展示服务端的新报价并停用旧卡片。网络、超时、5xx 和不完整成功结果按结果未知处理，不自动重放修改请求。
- 前端将当前有效报价编号作为 `currentDraftId` 带入后续聊天。后端读取本人草稿，向同步与 SSE Agent 提供核验后的报价；过期、已替换只生成不可用上下文，越权仍拒绝。提示词允许直接复述有效报价，不要求重复试算。
- `currentDraftId` 是本轮讨论对象；明确下单仍需要独立的 `confirmedDraftId`。请求不传入报价金额、预算或归属来替代后端数据。

独立调用工具生成的新草稿不属于本接口的替换链，不能据此声称所有历史草稿都已在后端统一撤销。

## 最新真实 HTTP 与模型联调

为避免重启用户正在运行的服务，使用最新编译代码启动独立本地端口，连接实际 MySQL、Redis 和模型。使用专用游客 Session，仅创建报价，不传 `confirmedDraftId`。

8 项检查全部通过：

1. 通过 Agent 为编号 20 热豆浆 1 份、预算 30 元生成真实草稿，总额 8 元。
2. 调用修改接口变为 2 份，得到新草稿编号及 16 元报价。
3. 同步聊天携带新编号，回答 2 份、16 元及完整新编号，没有额外试算或订单结果。
4. SSE 同会话读取同一新报价，最终 `done` 同样回答 2 份、16 元及新编号，没有额外试算或下单。
5. 携带被替换的旧编号时，正常说明报价已失效，不阻断整段聊天，也不引用旧金额。
6. 另一游客引用新草稿时返回 HTTP 403，在模型调用前拒绝。
7. 仅使测试自身草稿过期后，正常说明失效，不补造报价或订单。
8. 不带当前草稿引用的普通问候仍可正常回复。

失效回复没有显示 `UNAVAILABLE` 或 `currentDraftContext` 等内部标识。真实模型输出存在随机性，本次成功不代替后端权限与金额校验。
