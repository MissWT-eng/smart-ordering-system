1.用户表(user)：

用户id（主键）

用户手机号(唯一标识 、NOT NULL 、phone_number)

用户昵称(nickname 、可以为空),

用户创建日期(user_created_time, ATUO自动创建，默认当前时间)

用户状态(user_status 如果用户需要停止当前会员状态，就设为停用)

余额(balance，目前不用为未来留个口子)





2.菜品表(dish)：

菜品号(dish_number 唯一标识 、 NOT NULL 、自动增加)

菜品名(dish_name 和菜品号唯一对应)

菜品状态(dish_status 用来给商户表示当前菜品是否今日可以制作)

菜品介绍(dish_introduction 可以展示给前端，主作用还是后端到时候获取菜品介绍传给ai，让rag增强查询的结果更加准确)

价格(price DECIMAL(10,2))

菜品类型(category 枚举类型'meat', 'vegetable','drink')





3.用户历史订单记录表(orders) : 

订单编号（order_num 自动增加 主键）

订单用户id（order_user_id` 为外键，指向user(user_id))

本条订单金额(order_money)

订单时间(order_time DEFAULT CURRENT_TIMESTAMP)

订单状态(order_status ENUM('pending', 'paid', 'cancelled') DEFAULT 'pending')





4.用户历史订单记录详细表(order_item)：

详细表的 item_id (主键，自增)
订单表编号order_num (外键关联 orders.order_num)
菜品编号 dish_number (外键关联 dish.dish_number)
数量 quantity (INT DEFAULT 1)
下单时的价格 price_at_time (DECIMAL(10,2))





5.AI推荐记录表(recommendation_log) ： 

用户id，推荐菜品(的编号)（recommendation_dish_list JSON）

实际点菜品(的编号)(fact_dish_list JSON) 

当天天气情况(weather)

推荐时间(recommendation_time)

反馈分数(feedback_score（TINYINT，1-5分)，可以让服务员或者通过后面算法计算推荐预期值)

context(为ai补充上下文缺失部分,就比如上次用户点餐这种特征)





6.商户操作日志(operation_log) : 

操作人（operator）

操作类型(operation_type)

修改内容(operation_content)

操作时间(operation_time)


7.用户长期口味画像表(user_preference，M2 首版设计)：

设计更新日期：2026-10-21。本地画像表、本人 CRUD、Agent 读取和候选工具已实现并分阶段验证；候选结构化响应、独立确认保存及前端界面已接入，验证范围见[前端记录](m2-frontend-verification.md)。

- 用户编号 `user_id`：主键，同时关联 `user.user_id`，一名用户最多一条画像，不自增、不额外生成 UUID。
- 辣度偏好 `spicy_level`：复用 `SpicyLevel` 的 `none / mild / medium / high`；允许 `NULL` 表示未设置，`none` 表示明确偏好不辣。
- 补充口味说明 `preference_text`：最多 200 字，例如“喜欢清蒸、偏酸甜”，允许为空。
- 首次保存时间 `created_at`、最近修改时间 `updated_at`：使用 `DATETIME`，Java 对应 `LocalDateTime`。

首版只持久化注册用户明确确认的偏好，用户身份由后端根据有效 token 获取。游客对话、本轮人数、整单预算及完整聊天记录不写入本表。普通长期口味作为缺省条件，本轮明确提出的要求优先。

本人画像接口支持查看、整份替换保存、字段清空和整份删除，聊天入口每轮读取当前画像。候选工具保留未修改字段并主动校验，只返回待确认数据；候选作为结构化字段返回界面，由用户核对后通过独立画像接口保存。LLM 声称“已确认”不能直接触发写入。订单评分继续使用现有反馈数据，与明确设置的画像分开管理。

可执行 SQL 和字段约束见[数据库建表语句的 M2 用户长期画像章节](智能点餐系统数据库建表语句.md#m2-用户长期画像新表-sql)。
