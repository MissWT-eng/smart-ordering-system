# 智能点餐系统第一版需求文档

## 1. 文档目标

第一版目标是完成一个可以运行、演示和验证的智能点餐系统，重点体现：

- 注册用户和游客的识别与点餐；
- 菜单数据的维护；
- Agent 根据用户需求、天气和在售菜单生成推荐；
- 推荐结果经过后端校验后才能进入订单；
- 注册用户可以查询历史订单；
- 订单创建、异常处理和推荐日志形成完整闭环。

第一版采用模块化单体架构，先保证业务闭环和可验证性。

## 2. 用户角色

### 2.1 注册用户

注册用户通过手机号识别。系统可以查询其历史订单，并在用户同意的业务流程内将历史点餐信息提供给 AI 推荐模块。

### 2.2 游客

手机号未注册时，系统将当前访问者视为游客，不创建用户记录。游客可以查看菜单、获得推荐并创建订单，但不能查询历史订单。

游客的本次需求、推荐结果和身份信息不写入长期记忆或向量库。

### 2.3 商户操作人员

第一版通过管理接口维护菜单，不要求实现完整的商户登录和独立商户前端。后续可以增加管理页面和权限系统。

## 3. 第一版功能范围

### 3.1 用户识别

1. 支持通过手机号查询注册用户。
2. 支持注册新用户，手机号必须唯一。
3. 查询不到手机号时，不返回系统错误，允许以游客身份继续点餐。
4. 第一版不实现人脸识别、OCR、短信验证码和复杂账号体系。

### 3.2 菜单管理

管理接口支持：

- 新增菜品；
- 修改菜品名称、介绍、价格和分类；
- 查询菜单；
- 上架和下架菜品。

只有上架菜品可以被推荐或加入新订单。菜单价格以数据库中的当前价格为准。

### 3.3 AI 菜品推荐

用户可以提交以下需求：

- 用餐人数；
- 预算；
- 口味偏好；
- 忌口信息；
- 可选的补充说明。

系统根据用户类型使用不同上下文：

- 注册用户：本次需求、当前天气、在售菜单和必要的历史订单信息；
- 游客：本次需求、当前天气和在售菜单，不读取历史订单。

Agent 可以调用以下工具：

- 查询当前在售菜单；
- 查询注册用户历史订单；
- 查询天气。

推荐结果至少包含：

- 推荐菜品编号；
- 推荐理由；
- 预计总价。

模型返回结果后，后端必须重新查询数据库，校验菜品是否存在、是否上架、价格是否有效以及是否满足预算。模型不得直接写入订单或决定最终金额。

用户可以接受推荐，也可以修改或补充菜品后再下单。

### 3.4 订单创建

注册用户和游客都可以创建订单。

创建订单时，后端必须：

1. 校验请求参数和菜品数量；
2. 查询所有菜品的当前状态和价格；
3. 拒绝不存在或已下架的菜品；
4. 根据数据库价格重新计算订单总额；
5. 在一个事务中保存订单和订单明细；
6. 保存下单时的菜品价格快照。

游客订单不关联 `user` 记录。注册用户订单关联对应的 `user_id`。

第一版不接入真实微信或支付宝支付，订单先支持 `pending`、`paid`、`cancelled` 状态的基础模型，其中支付状态只通过测试接口或管理接口变更。

### 3.5 历史订单

注册用户可以按手机号或用户 ID 查询自己的历史订单，结果支持分页。

历史订单至少展示：

- 订单编号；
- 下单时间；
- 订单状态；
- 订单总额；
- 菜品名称、数量和下单时价格。

游客没有历史订单查询能力。

### 3.6 推荐日志

注册用户的推荐可以记录：

- 用户 ID；
- 推荐菜品；
- 实际下单菜品；
- 推荐时天气；
- 推荐时间；
- 推荐是否被采纳。

游客推荐不保存个人身份信息，也不写入长期记忆或向量库。第一版暂不要求统计游客推荐效果。

推荐日志只是分析数据，不得作为订单事实来源。

### 3.7 基础异常处理

系统至少处理以下异常：

- 请求参数格式错误；
- 手机号格式错误；
- 菜品不存在；
- 菜品已下架；
- 订单菜品数量不合法；
- 订单创建事务失败；
- AI 模型调用超时或失败；
- AI 返回格式错误；
- AI 推荐了不存在或不满足条件的菜品。

AI 推荐失败时，用户仍然可以查看菜单并手动创建订单。辅助功能失败不能阻断普通点餐流程。

## 4. 第一版明确不做的内容

- 人脸识别和 OCR；
- 短信验证码登录；
- 多商户隔离；
- 完整角色权限系统；
- 真实支付；
- 剩菜图像识别和自动满意度判断；
- 多 Agent 协作；
- 微服务拆分；
- 复杂推荐算法和模型微调。

## 5. 核心验收场景

### 场景一：注册用户点餐

给定一个已注册手机号，用户提交人数、预算和口味要求。系统能够查询用户历史订单和当前菜单，生成推荐；
用户确认后创建订单，订单金额由后端根据数据库价格计算。

### 场景二：游客点餐

给定一个未注册手机号或不提供手机号的访问者，
系统不创建用户记录，但允许其查看菜单、获得基于天气和本次需求的推荐并创建订单。该订单的 `user_id` 为空。

### 场景三：推荐结果校验

当模型返回已下架或不存在的菜品时，后端拒绝非法菜品，不允许其进入订单，并返回可理解的处理结果。

### 场景四：模型失败降级

当模型调用超时或返回格式错误时，系统记录错误并返回可用的降级结果，用户仍可以手动选择菜单并创建订单。

### 场景五：订单事务

当订单主表或订单明细保存失败时，整笔订单回滚，不留下只有主表或只有明细的脏数据。

### 场景六：用户数据隔离

注册用户 A 查询历史订单或请求推荐时，不能读取注册用户 B 的历史订单和长期偏好。

## 6. 第一版完成标准

满足以下条件时，第一版视为完成：

1. 普通菜单查询、游客点餐和注册用户点餐均可运行；
2. AI 推荐能够调用至少一个业务工具，并经过后端校验；
3. 订单金额、菜品状态和用户数据不依赖模型判断；
4. 主要正常和异常场景有可重复测试记录；
5. 项目可以在本地启动，并有数据库初始化和运行说明；
6. 能够解释主要模块的职责、关键技术选择和失败处理方案。
