# 智能点餐系统第二版需求文档（V2 · 点餐助手 Agent）

## 1. 文档目标

在第一版（RAG 推荐 + 后端接口）的基础上，把现有能力「工具化」，上套 LLM Agent 大脑，使系统从「被动问答的推荐生成器」进化为「能理解自然语言、自主规划多步、调用工具、记住用户、主动建议的点餐助手」。

V2 不推翻 V1，而是复用 V1 的全部资产：DeepSeek（支持 function calling）、BGE-M3 + Qdrant 菜品检索、现有所有后端接口与 Service。V2 的核心增量是三层：工具调用、记忆、自主规划。

## 2. 与 V1 的关系

- V1 的 RAG 推荐与后端接口在 V2 中降级为 Agent 的「工具」。
- V1 的 Controller（给前端 HTTP 用）保持不变；V2 新增独立的 Agent 入口（`/agent/chat`），两者共享底层 Service，互不替代。
- V1 的鉴权、订单、菜单、天气、反馈体系全部沿用并增强。

## 3. 用户角色（沿用 V1）

- **注册用户**：通过手机号识别，可查历史订单；V2 中 Agent 以其身份（携带 `X-User-Token`）调用工具，可读取其历史订单与画像。
- **游客**：未注册，V2 中 Agent 以游客身份调用工具，不可读历史订单与画像，订单 `user_id` 为空。
- **商户操作人员**：通过 `/admin/**` 管理接口，V2 不涉及商户端的 Agent 化。
- **Agent 作为执行者**：Agent 本身不是用户，它以「当前会话的用户身份」调用工具，不得越权读取或写入他人数据。

## 4. V2 功能范围（按里程碑）

### 4.1 M1 · 工具执行型 Agent（第一里程碑，最小可行 V2）

- 新增 Agent 入口 `/agent/chat`，接收自然语言 + 用户身份（`userId` / `token` 或游客）。
- 把以下能力封装为 LangChain4j `@Tool`，由 LLM 自主决定何时调用：
  - `query_menu`：查在售菜单 / 按分类筛选；
  - `recommend_dishes`：按口味 / 人数 / 预算生成推荐（**预算为后端硬约束**）；
  - `draft_order`：生成订单草稿（只读计算，**不落库**）；
  - `confirm_order`：真正落库（调 `orderService.createOrder`）；
  - `get_weather`：天气，辅助推荐。
- **写操作必须走「人工确认闸门」**：Agent 先出 `draft`，用户确认后才 `confirm`；LLM 不得直接写数据库。
- **LLM 不得直接写库**：所有数据写操作经 `confirm_order` 这一道工具；模型只负责决策与编排。
- 身份在 Agent 链路正确透传：注册用户携带 token，Agent 内部工具可查其历史订单；游客不携带。
- 工具失败（LLM 超时 / Redis 异常）有降级，不阻塞点餐。

### 4.2 M2 · 记忆型 Agent

- 用户画像持久化（忌口、常点、预算习惯），跨会话记忆。
- 主动提醒（如「这桌要不要少点甜品？」）。
- 顺带实现 token 降级（Redis 异常 → fail-closed 返回 401，全站不 500）。
- 引入 `chatMemory`（短期会话记忆）。

### 4.3 M3 · 主动自治 Agent（运营 copilot）

- 定时任务 + Agent：按天气 / 历史销量 / 库存，自动生成「今日套餐」与「备货预警」。
- Agent 自主运行，不等人问。

### 4.4 M4 · 多 Agent 编排 / 场景化（可选，远期）

- 总控 Agent + 推荐 / 下单 / 客服 / 库存专家 Agent 协作复杂任务。
- 场景化：语音点餐、拍菜单识别、拍剩菜推荐等。

## 5. V2 明确不做（V1 不做项继续不做，并新增）

- 真实支付（维持 `pending` / `paid` / `cancelled` 基础模型）。
- 短信验证码登录（M2 前不做；登录无验证码的已知风险在 V1 已记账）。
- 人脸识别 / OCR / 图像识别。
- 微服务拆分、多商户隔离。
- 复杂 RAG 微调、模型训练。
- V1 的推荐逻辑被 Agent 的 `recommend_dishes` 工具取代，但底层 `RecommendationService` 逻辑保留复用。

## 6. 核心验收场景（M1 阶段）

### 场景一：自然语言点餐闭环

用户说「给这桌配个不辣的 4 人套餐，预算 200」→ Agent 自主：查菜单 → 按人数 / 预算 / 忌口筛选 → 出推荐 → 生成订单草稿 → 用户确认 → 真下单。全流程可跑通。

### 场景二：预算硬约束

Agent 调 `recommend_dishes`，后端贪心砍菜，最终推荐总价 ≤ 预算；LLM 不得自行放宽预算。

### 场景三：人工确认闸门

`draft_order` 调用后数据库无新订单；`confirm_order` 调用后才落库。Agent 不能一句话直接下真单。

### 场景四：身份透传与数据隔离

注册用户带 token 时，Agent 内部可查其历史订单；游客不带时不可查。用户 A 不能借 Agent 读到用户 B 的数据。

### 场景五：工具 / LLM 失败降级

LLM 超时或某工具异常时，Agent 返回可读降级提示，用户仍可走 V1 前端手动点餐；V2 故障不拖垮 V1。

### 场景六：V1 既有接口不受影响

V1 前端（`user-frontend`）所有功能、商户接口（`/admin/**`）在 V2 新增后仍正常，无回归。

## 7. V2 完成标准（以 M1 完成为 V2 首个可验收节点）

1. `/agent/chat` 能处理自然语言点餐，完成「查菜单 → 推荐 → 草稿 → 确认 → 下单」闭环；
2. 写操作全部经 `confirm` 闸门，LLM 不直接写库；
3. 用户身份在 Agent 链路正确透传，数据隔离不破坏；
4. 工具与 LLM 失败有降级，不阻塞 V1；
5. 每个 `@Tool` 的 `name` / `value` 说明书清晰，能解释 Agent 为何调它；
6. 本地可启动，有 Agent 调用说明与测试记录；
7. 能解释 Agent 装配（`AiServices`）、`@Tool` 机制、ReAct 循环、人工确认闸门的设计意图。
