# 智能点餐系统第二版需求文档（V2 · 点餐助手 Agent）

## 1. 文档目标

在 V1 的推荐服务与后端接口基础上，新增自然语言点餐 Agent，复用现有 Service 完成候选推荐、草稿试算、人工确认和正式下单。

沿用 LangChain4j、DeepSeek 对话模型、BGE-M3 向量化和 Qdrant 菜品检索，不为新增 Agent 重建原有推荐与订单体系。

V2 按里程碑推进：M1 完成工具执行与可靠下单，M2 增加对话记忆和长期画像，M3/M4 为后续扩展。M1 是 V2 首个可验收节点，不要求同时交付后续里程碑。

本文区分需求目标和当前实现边界。实现状态更新至 2026-10-18；后续变更时同步更新。“已有实现”与“场景验收通过”分别记录。本轮短期记忆基础验收及核心下单联调范围见 [验证记录](m2-memory-verification.md)，不代表整个 M1/M2 计划已全部完成。

## 2. 与 V1 的关系

- V1 的推荐、菜单、订单、天气和反馈 Service 供 Agent 工具复用。
- V1 的 HTTP 接口及前端继续可用；V2 新增 `/agent/chat`，不替代原接口。
- Agent 理解需求并选择工具；身份、菜品状态、金额、确认授权和订单事实由后端校验。
- V2 的确认规则约束 Agent 创建正式订单；V1 手动下单沿用原入口和业务校验。

## 3. 用户角色与身份边界

- **注册用户**：请求携带 `X-User-Token`。后端校验后获取真实用户 ID 并生成 `ownerKey`，不信任客户端或模型自行指定的身份。当前身份已用于草稿归属和正式下单；个性化推荐与 Agent 历史订单查询待补齐。
- **游客**：不携带用户 token，通过 HTTP Session 确定草稿归属。游客订单的 `order_user_id` 为空，不读取注册用户历史订单或画像。跨请求操作同一草稿时，客户端须保留同一会话 Cookie。
- **商户操作人员**：通过 `/admin/**` 管理菜单和订单；M1/M2 不增加商户 Agent 入口，运营助手属于 M3 扩展。
- **Agent**：以当前请求的可信身份调用工具，不能通过自然语言改变身份、确认授权或草稿归属。

## 4. V2 功能范围（按里程碑）

### 4.1 M1 · 工具执行型 Agent

#### 4.1.1 入口与调用上下文

`POST /agent/chat` 接收自然语言 `message`、可选的 `conversationId` 和 `confirmedDraftId`。不传会话编号时开启新聊天，后续请求携带返回的编号。普通推荐、试算请求不传确认字段；用户明确确认某份已展示报价的草稿时，客户端提交该草稿编号。

后端通过 `InvocationParameters` 传递可信的 `ownerKey` 和本次 `confirmedDraftId`。模型只提供业务参数，不能生成或修改调用身份与确认授权。文本中的“已确认”不能代替确认字段。

当前入口返回 `ApiResponse<AgentChatResponse>`，`data` 包含 `conversationId` 与文本 `reply`，草稿编号及报价来自工具结果。后续如增加确认按钮，可提供结构化草稿与订单结果，不以解析模型自由文本作为订单事实来源。

#### 4.1.2 工具职责与当前边界

本文使用当前代码的工具方法名，不另用 `snake_case` 别名。

| 能力 | 职责 | 当前实现边界 |
| --- | --- | --- |
| `queryMenu` | 查询在售菜单 | 已有工具，返回全部在售菜品；按分类筛选待补齐 |
| `recommendDish` | 按口味、人数及可选预算返回候选菜品与单价 | 已有工具；当前按游客上下文调用，注册用户个性化上下文待补齐 |
| `draftOrder` | 根据菜品编号、份数及可选预算核价并生成临时草稿 | 已有工具，Redis 保存报价、编号、归属及有效期，不创建正式订单 |
| `confirmOrder` | 核对本次确认并提交指定草稿，或返回其已有订单 | 已有工具，调用草稿 Service 和订单 Service |
| 天气查询 | 为推荐提供天气上下文 | 推荐服务内部已有查询；原规划的独立天气工具尚未接入，仍为 M1 待补齐目标 |
| 本人历史订单查询 | 注册用户查询本人历史订单 | V1 已有接口；Agent 工具尚未接入，仍为 M1 待补齐目标 |

模型按需求选择工具，不要求每次严格执行固定顺序。正式下单必须经过真实草稿试算与确认校验。

#### 4.1.3 候选推荐与预算规则

- `recommendDish` 返回候选列表，不是含确定份数的套餐报价；候选列表价格合计不作为订单总额。
- 当前候选筛选排除单价超过所传预算的菜品。套餐总额由 `draftOrder` 按数据库价格和实际份数计算。
- 预算可不提供，此时不作预算结论；提供预算时，草稿返回总额和 `overBudget`。超预算草稿可展示，不能确认下单。
- 用户明确给出的预算必须保留到草稿，模型不得省略或提高。当前预算通过工具参数传入，对原话到草稿的传递仍需验收，不能仅凭草稿校验认定全过程已满足约束。
- 用户调整菜品、数量或预算后生成新草稿，展示新报价并等待再次确认。需求不指定“贪心砍菜”等算法。
- 区分口味建议和可验证的限制。没有可靠菜品数据支持的配料、忌口判断须说明信息不足，不宣称已保证满足。

#### 4.1.4 临时草稿与人工确认

- 后端生成 `draftId`，保存报价明细、预算、`ownerKey`、创建时间和有效期。允许写入临时缓存，不写入正式订单主表和明细。
- 草稿有效期由 `auth.draft-ttl-minutes` 配置，当前默认 15 分钟。生成后展示菜品、份数、单价、小计、总价、预算结论、编号和有效期，说明尚未正式下单。
- `confirmOrder` 的目标 `draftId` 必须与本次 `confirmedDraftId` 一致。后端核对归属、有效期、预算及当前菜品状态和价格，不能只靠提示词判断是否允许下单。
- 过期、超预算、菜品下架或价格变化时拒绝首次提交，要求重新试算、展示报价并再次确认。
- 同一草稿再次确认时返回已有订单，并核对订单归属。已取消订单如实返回，不自动创建替代订单。
- 并发确认由订单表的 `draft_id` 唯一约束保障同一草稿最多创建一笔订单。当前本地唯一约束已确认，并发 HTTP 请求已验证返回同一订单，数据库仅有一笔主订单和一套明细；实际触发重复键捕获分支的确定性验证仍待补齐。
- 正式订单在事务中保存，金额及价格快照来自后端查询。日志和临时状态保存不要求用户逐次确认。
- 聊天记忆不能替代草稿、确认授权或订单事实。M1 可通过明确草稿编号和确认字段完成跨请求下单；M2 当前已接入跨轮短期上下文，正式下单仍需本次确认字段和后端校验。

#### 4.1.5 故障边界

- 推荐理由或天气查询失败时，返回可读结果或跳过辅助信息；用户仍可查看菜单并通过 V1 手动点餐。
- LLM 或工具失败时，不编造报价、草稿及订单，不把失败当成成功。
- token 无效或过期时拒绝受保护操作；身份服务不可用时也拒绝相关操作，但须与凭证无效区分提示。该降级属于 M1 待验收要求，不重复放入 M2。
- Redis 无法读取草稿时停止首次确认，不绕过归属和报价检查。故障不应阻断不依赖 Redis 的菜单查询及游客手动下单。
- 订单可能已提交而模型回复失败。恢复时按草稿查询已有订单，重复确认不创建新订单；不能仅凭聊天超时判定订单创建失败。
- 当前通用异常兜底不代表上述故障场景均已验证，需记录实际行为。

### 4.2 M2 · 记忆型 Agent 与对话体验

- **短期上下文已接入**：通过 `@MemoryId` 和 `chatMemoryProvider` 为每段聊天创建独立的 `MessageWindowChatMemory`，窗口为 20 条消息；人数、预算、口味跨轮复述已验证。“换掉刚才那道菜”等真实多轮点餐编排仍需补充演示验收。
- **会话归属已实现**：编号由后端生成 UUID，Redis 保存可信 `ownerKey`；使用前校验存在性及归属。已验证同一游客的新旧聊天隔离和两个独立游客会话的双向越权拒绝，注册用户间的记忆隔离验收待补齐。
- **固定期限与清理已实现**：会话默认从创建起 30 分钟有效，当前不会自动续期。请求使用计数与空闲过期清理通过同一编号的 `compute` 协调，定时检查间隔为前一轮结束后 60 秒；调用中保护、内容及缓存移除、Redis 异常保留和重试已完成临时程序验证。
- **存储边界**：聊天消息保存在 Java 进程内；Redis 保存归属。重启后本机记忆丢失，尚无共享聊天记忆、完整历史归档、本机总容量上限或同会话消息执行顺序保障。游客短期上下文不写入长期画像或向量库。
- **会话续期待做**：确定滑动有效期和续期时机，确保有效归属检查与刷新协调，越权或已过期编号不能续期；补充续期与清理竞争的验收。
- **长期画像待做**：持久化注册用户跨会话偏好、常点和预算习惯；首版优先结构化偏好及明确保存意图，提供本人画像查看、更正及删除能力，不把本轮临时需求直接变成长期习惯。
- **主动提醒与体验待做**：根据当前方案提供数量或搭配提醒，不能擅自修改草稿或提交订单。流式响应和前端增量展示需处理断线、超时与重试，不放宽确认和重复提交约束。学习与实施待办见 `docs/TODO.md`。

### 4.3 M3 · 运营助手（后续扩展）

- 定时根据天气和历史销量生成今日套餐、备货建议，由商户审核后使用。
- 真实库存预警依赖库存、原料与菜品关系及消耗记录，须先补齐数据模型；只有销量数据时不宣称能提供真实库存预警。
- 首阶段只生成建议，不自动上架、采购或修改订单。

### 4.4 M4 · 多 Agent 与场景扩展（可选、远期）

- 总控 Agent 与推荐、客服、库存等专家 Agent 协作，是否拆分由实际复杂度决定。
- 语音点餐、菜单识别等另行定义需求，不属于 M1/M2 验收。

## 5. M1/M2 明确不做的内容

- 真实支付，维持 `pending` / `paid` / `cancelled` 基础模型；下单成功不等于支付或制作完成。
- M1 不增加短信验证码登录，沿用 V1 手机号识别；token 校验不代表已验证手机号持有者，登录升级另行定义。
- 人脸识别、OCR、剩菜图像识别。
- 微服务拆分、多商户隔离、模型训练和复杂 RAG 微调。
- 自动采购、自动运营写操作和多 Agent 编排。

## 6. 核心验收场景（M1）

### 场景一：自然语言点餐闭环

用户提出“不辣、4 人、预算 200”，Agent 根据需求获取候选菜品，提出搭配和份数，调用 `draftOrder` 展示真实报价。用户明确确认并提交该 `confirmedDraftId` 后，`confirmOrder` 返回正式订单。

验收关注实际菜品、份数、预算、确认和订单结果，不限定工具顺序。没有可靠数据支持的忌口结论须说明限制。跨请求确认可明确携带草稿编号；M2 已接入短期上下文，真实多轮点餐场景仍单独验收。

### 场景二：预算硬约束

候选列表不作为套餐报价。验证用户预算准确传入草稿，后端按单价乘份数计算总额；总额等于预算时允许确认，超过预算时拒绝首次提交。模型省略、提高预算或自行宣称满足预算不能通过验收。用户明确调整预算后须重新试算并确认。

### 场景三：人工确认闸门与草稿变化

- 生成草稿后，正式订单主表和明细无新增记录，允许存在 Redis 临时草稿。
- 没有确认字段、编号不匹配或仅要求“推荐完直接下单”时，不创建订单。
- 草稿过期、超预算、菜品下架或价格变化时，拒绝首次提交并要求重新试算、确认。
- 修改菜品、数量或预算后展示新草稿，不在同一轮自动提交新报价。

### 场景四：身份透传与数据隔离

- 注册用户身份来自有效 token，草稿和订单关联正确用户；游客订单不关联注册用户。
- 用户 A 不能确认用户 B 的草稿或读取其已有订单；两个游客 Session 同样互相隔离。
- Agent 历史订单工具接入后，仅允许查询本人，游客和越权请求被拒绝。注册用户个性化推荐使用可信身份，不继续按游客上下文调用。
- 历史订单工具和个性化推荐尚未接入，不能标记对应项已通过。

### 场景五：重复确认与并发提交

同一草稿连续确认返回相同订单编号。并发确认只产生一笔主订单和一套明细。验证实际数据库存在 `draft_id` 唯一约束，不能仅以捕获重复键异常作为证明。已有订单重试读取仍需校验归属，即使临时草稿已过期，也不重新创建订单。

### 场景六：工具与 LLM 失败降级

验证 LLM 超时、天气失败、Redis 草稿读写失败和身份服务不可用时的提示及限制。用户仍可使用不受故障影响的 V1 功能。额外验证“订单已提交、最终模型回复失败”：按草稿恢复订单结果，不重复下单。

### 场景七：V1 既有接口不受影响

V1 用户端菜单、推荐、手动下单、历史查询及商户接口在 V2 新增后仍正常。注册用户和游客均覆盖；新增订单草稿字段不影响原手动下单。

## 7. M1 完成标准

1. `/agent/chat` 完成候选推荐、真实草稿试算、明确确认和正式下单闭环。
2. Agent 创建正式订单经过后端确认闸门，模型不能绕过身份、预算、报价及菜品状态校验。
3. 注册用户和游客的草稿及订单归属正确；历史订单工具、个性化推荐、菜单分类筛选和独立天气工具完成接入及对应验收。推荐内部天气查询不等于独立工具已实现。
4. 重复及并发确认最多创建一笔订单，数据库约束与回复失败后的恢复行为有验证记录。
5. 工具与 LLM 故障有可读降级，受保护操作不会因降级而越权，V1 可用路径不被 V2 故障阻断。
6. 工具说明、参数及结构化结果清晰，本地启动、数据库初始化、Agent 请求与确认流程有说明。
7. 主要正常、拒绝、故障、并发及 V1 回归场景有可重复测试记录；代码机制、编译通过与场景验收通过分别记录。
8. 能解释 `AiServices` 装配、工具执行循环、临时草稿、可信调用上下文、人工确认和重复提交保护的设计。
