# 智能点餐系统第二版需求文档（V2 · 点餐助手 Agent）

## 1. 文档目标

在 V1 的推荐服务与后端接口基础上，新增自然语言点餐 Agent，复用现有 Service 完成候选推荐、草稿试算、人工确认和正式下单。

沿用 LangChain4j、DeepSeek 对话模型、BGE-M3 向量化和 Qdrant 菜品检索，不为新增 Agent 重建原有推荐与订单体系。

V2 按里程碑推进：M1 完成工具执行与可靠下单，M2 增加对话记忆和长期画像，M3/M4 为后续扩展。M1 是 V2 首个可验收节点，不要求同时交付后续里程碑。

本文区分需求目标、已有实现和场景验收。实现状态更新至 2026-11-10：M2 核心流程已完成分阶段验收，后续新增天气共享缓存、报价编辑、订单结果核实、评分重排、语音体验、推荐数量约束、历史订单工具及菜单分类筛选；M3/M4 尚未开始。最新范围见[体验打磨清单](m2-refinement-todo.md)、[前端验证](m2-frontend-verification.md)和[语音验证](m2-speech-verification.md)。分阶段结果不等于全部故障、V1 回归或生产场景均已通过。

## 2. 与 V1 的关系

- V1 的推荐、菜单、订单、天气和反馈 Service 供 Agent 工具复用。
- V1 的 HTTP 接口及前端继续可用；V2 新增 `/agent/chat` 与 `/agent/chat/stream`，用户端默认进入 AI 点餐，保留快捷点餐、菜单与订单入口。
- Agent 理解需求并选择工具；身份、菜品状态、金额、确认授权和订单事实由后端校验。
- V2 的确认规则约束 Agent 创建正式订单；V1 手动下单沿用原入口和业务校验。

## 3. 用户角色与身份边界

- **注册用户**：请求携带 `X-User-Token`。后端校验后获取真实用户 ID 并生成 `ownerKey`，不信任客户端或模型自行指定的身份。身份用于草稿、正式订单、画像、本人评分、推荐重排及历史订单查询；Agent 历史订单工具只接受后端传入的用户编号，不接受模型或请求体指定他人身份。语音输入与朗读首版也要求登录。
- **游客**：不携带用户 token，通过 HTTP Session 确定草稿归属。游客订单的 `order_user_id` 为空，不读取注册用户历史订单或画像。跨请求操作同一草稿时，客户端须保留同一会话 Cookie。
- **商户操作人员**：通过 `/admin/**` 管理菜单和订单；M1/M2 不增加商户 Agent 入口，运营助手属于 M3 扩展。
- **Agent**：以当前请求的可信身份调用工具，不能通过自然语言改变身份、确认授权或草稿归属。

## 4. V2 功能范围（按里程碑）

### 4.1 M1 · 工具执行型 Agent

#### 4.1.1 入口与调用上下文

`POST /agent/chat` 接收自然语言 `message`，以及可选的 `conversationId`、`currentDraftId` 和 `confirmedDraftId`。不传会话编号时开启新聊天，后续请求携带返回的编号。`currentDraftId` 仅指定当前讨论的报价；用户明确确认某份已展示报价时，客户端另行提交该草稿的 `confirmedDraftId`。

后端通过 `InvocationParameters` 传递可信的 `ownerKey` 和本次 `confirmedDraftId`。模型只提供业务参数，不能生成或修改调用身份与确认授权。文本中的“已确认”不能代替确认字段。

M2 同时通过后端调用上下文传递已解析的 `userId`、`userToken` 与已查询的 `userPreference`，供推荐 Service 读取本人反馈、候选工具保留原画像字段。模型可见的画像上下文仅包含两个口味字段，凭证不进入工具参数或提示词。当前报价由后端按身份读取并核验后，再向 Agent 提供结构化报价上下文。

同步入口返回 `ApiResponse<AgentChatResponse>`，`data` 包含 `conversationId`、文本 `reply` 及可空的 `proposalToolResult`、`draftToolResult`、`orderToolResult`。工具字段来自本轮真实执行对象，各自以最后一次调用为准。前端据此生成口味候选、报价与订单回执，不从自由文本解析订单事实。

`POST /agent/chat/stream` 接收相同请求体，通过同一 Agent、工具及会话记忆输出 SSE。事件顺序为 `meta → delta… → done`，模型失败时使用 `error`；`done` 的数据为完整 `AgentChatResponse`。入口错误仍使用 HTTP 错误状态和 JSON。两种入口共享 4 个并发许可，`message` 最多 2000 字。

#### 4.1.2 工具职责与当前边界

本文使用当前代码的工具方法名，不另用 `snake_case` 别名。

| 能力 | 职责 | 当前实现边界 |
| --- | --- | --- |
| `queryMenu` | 查询在售菜单，可按分类筛选 | 已支持 `meat` / `vegetable` / `drink` / `soup` 四类；未传分类时返回全部在售菜品。分类是菜品大类，不代表菜系或忌口 |
| `recommendDish` | 按口味、人数、可选预算及可选菜品数量返回候选菜品与单价 | 长期口味默认上下文与可信用户身份已接通，推荐 Service 使用本人评分重排；`dishCount` 已约束返回数量（1～5 道），换一道与相似新菜泛化待完善 |
| `draftOrder` | 根据菜品编号、份数及可选预算核价并生成临时草稿 | 已有工具，Redis 保存报价、编号、归属及有效期，不创建正式订单 |
| `confirmOrder` | 核对本次确认并提交指定草稿，或返回其已有订单 | 已有工具，调用草稿 Service 和订单 Service |
| `queryWeather` | 查询门店城市当前天气，为推荐提供上下文 | 独立工具已接入，工具与推荐共用按城市保存的 Redis 短时缓存；任意城市和预报待设计 |
| `proposeUserPreference` | 生成待用户核对的长期口味候选 | 已接入，返回候选不直接保存；前端通过独立 PUT 明确确认 |
| `queryOrderHistory` | 查询注册用户本人最近 5 笔历史订单 | 已接入，复用 `OrderService.queryOrders`；身份取自后端调用上下文，工具签名不含用户编号；游客返回 `LOGIN_REQUIRED`，无订单返回 `NO_ORDERS` |

模型按需求选择工具，不要求每次严格执行固定顺序。正式下单必须经过真实草稿试算与确认校验。

分类筛选取自 `dish.category`，只有 `meat` / `vegetable` / `drink` / `soup` 四个枚举值，不等于菜系或忌口，无法回答“凉菜”“下酒菜”这类说法。当前数据存在含肉菜品登记为 `vegetable` 的情况（如麻婆豆腐、干锅花菜），素食需求不能仅凭分类承诺不含肉，须以菜品简介和门店确认为准。

#### 4.1.3 候选推荐与预算规则

- `recommendDish` 返回候选列表，不是含确定份数的套餐报价；候选列表价格合计不作为订单总额。
- 外层 Agent、内层推荐模型和工具指引已统一为推荐阶段仅展示候选及单价；不以“约”等措辞估算组合金额，用户要求不试算时不生成草稿。模型不得自行心算或加减合计；如需提示预算，只能引用后端计算的 `unitPriceSum`（候选菜品各一份的单价合计），并说明这是按每道一份的估算、不是订单金额、实际金额以 `draftOrder` 试算为准。真实对话已验证：指定 3 道返回 3 道，凑不齐时如实说明，未再出现模型自行汇总；候选数量偏差仍待优化。
- 当前候选筛选仅排除单价超过所传预算的菜品，**预算不约束整桌合计**：预算 50 元时仍可能返回多个单价 30～46 元的候选，合计远超预算属于当前设计的已知边界。套餐总额由 `draftOrder` 按数据库价格和实际份数计算；预算内的整桌配菜待后端推荐算法升级后另行定义。
- 召回数与返回数分别配置，当前为 20 / 5；先受约束召回，再核对在售状态、本人评分及单价预算，最终候选、理由与推荐记录保持一致。偏好解析失败明确返回不可用，条件检索为空不改成无条件检索。用户指定的 `dishCount` 上限（当前 5）须与 `recommendation.result-limit` 保持一致，修改配置时同步调整请求校验。
- 评分入口从有效 token 取得用户编号，覆盖请求体可能提供的身份。真实评分、向量候选对照与聊天工具联调已通过；首版为具体菜品反馈重排，改分规则、相似菜偏好与适度尝新仍待设计。
- 预算可不提供，此时不作预算结论；提供预算时，草稿返回总额和 `overBudget`。超预算草稿可展示，不能确认下单。
- 用户明确给出的预算必须保留到草稿，模型不得省略或提高。当前预算通过工具参数传入，对原话到草稿的传递仍需验收，不能仅凭草稿校验认定全过程已满足约束。
- 用户调整菜品、数量或预算后生成新草稿，展示新报价并等待再次确认。需求不指定“贪心砍菜”等算法。
- 区分口味建议和可验证的限制。没有可靠菜品数据支持的配料、忌口判断须说明信息不足，不宣称已保证满足。

#### 4.1.4 临时草稿与人工确认

- 后端生成 `draftId`，保存报价明细、预算、`ownerKey`、创建时间和有效期。允许写入临时缓存，不写入正式订单主表和明细。
- 草稿有效期由 `auth.draft-ttl-minutes` 配置，当前默认 15 分钟。生成后展示菜品、份数、单价、小计、总价、预算结论、编号和有效期，说明尚未正式下单。
- `confirmOrder` 的目标 `draftId` 必须与本次 `confirmedDraftId` 一致。后端核对归属、有效期、预算及当前菜品状态和价格，不能只靠提示词判断是否允许下单。
- 过期、超预算、菜品下架或价格变化时拒绝首次提交，要求重新试算、展示报价并再次确认。
- 同一草稿再次确认时返回已有订单，并核对订单归属。已取消订单如实返回，不自动创建替代订单。
- 并发确认由订单表的 `draft_id` 唯一约束保障同一草稿最多创建一笔订单。当前本地唯一约束已确认，并发 HTTP 请求已验证返回同一订单，数据库仅有一笔主订单和一套明细；实际触发重复键捕获分支的确定性验证仍待补齐。
- 正式订单在事务中保存，金额及价格快照来自后端查询。日志和临时状态保存不要求用户逐次确认。
- 聊天记忆不能替代草稿、确认授权或订单事实。M1 可通过明确草稿编号和确认字段完成跨请求下单；M2 当前已接入跨轮短期上下文，正式下单仍需本次确认字段和后端校验。
- 报价卡可调整原菜品数量或删除项，通过 `POST /order-drafts/{draftId}/revisions` 继承预算并生成新草稿。Redis Lua 原子替换旧报价，单实例 Guard 协调修改与确认；编辑后需按新编号再次确认。后续聊天携带 `currentDraftId` 读取核验后的新报价，换菜入口仍待实现。

#### 4.1.5 故障边界

- 推荐理由或天气查询失败时，返回可读结果或跳过辅助信息；用户仍可查看菜单并通过 V1 手动点餐。
- LLM 或工具失败时，不编造报价、草稿及订单，不把失败当成成功。
- token 无效或过期时拒绝受保护操作；身份服务不可用时也拒绝相关操作，但须与凭证无效区分提示。该降级属于 M1 待验收要求，不重复放入 M2。
- Redis 无法读取草稿时停止首次确认，不绕过归属和报价检查。故障不应阻断不依赖 Redis 的菜单查询及游客手动下单。
- 订单可能已提交而模型回复失败。恢复时按草稿查询已有订单，重复确认不创建新订单；不能仅凭聊天超时判定订单创建失败。
- 订单结果核实首版已实现：前端保留本次已确认的草稿编号，使用 `GET /order-drafts/{draftId}/order` 按可信身份只读查询 MySQL；`not_found` 保持待核实，不自动重发下单。原账号重新登录可继续核实，换账号清理；刷新页面后的持久恢复尚未实现。
- 当前通用异常兜底不代表上述故障场景均已验证，需记录实际行为。

### 4.2 M2 · 记忆型 Agent 与对话体验

- **短期上下文已接入并完成多轮演示**：通过 `@MemoryId` 和 `chatMemoryProvider` 为每段聊天创建独立的 `MessageWindowChatMemory`，窗口为 20 条消息。真实页面已验证人数、预算、口味跨轮使用，修改豆浆数量后重新核价、替换主菜后生成新草稿及明确下单，见[收尾记录](m2-closeout-verification.md)。
- **会话归属已实现**：编号由后端生成 UUID，Redis 的会话值保存 `ownerKey`、`instanceId` JSON；使用前校验存在性、归属及所属应用实例。已验证游客与两个注册用户的双向越权拒绝，以及本人记忆读取、同一用户换 token 续聊。
- **滑动期限与清理已实现**：默认有效期为 30 分钟；归属及实例校验通过后，通过同一段 Lua 刷新 TTL。过期、越权或实例失效请求不续期、不自动重建。请求使用计数与空闲过期清理通过同一编号的 `compute` 协调，定时检查间隔为前一轮结束后 60 秒；调用中保护、内容及缓存移除、Redis 异常保留和重试已有验证记录。
- **同会话并发拒绝已实现**：当前单实例中，同一 `conversationId` 同时只允许一条消息进入 Agent，其余返回 HTTP 409。受控测试中 12 条请求只允许一条进入模型，其余 11 条被拒绝；不同会话可同时处理。该限制不代表全局并发或多实例并发控制。
- **实例失效提示已实现**：每次创建会话 Service 实例生成一次 `instanceId`。归属正确但实例编号不同的旧会话返回 `CONVERSATION_CONTEXT_LOST`（HTTP 409），提示开启新对话；其他身份优先返回 403。旧格式纯 `ownerKey` 缓存也按归属拒绝，不能直接续期。已完成独立 Service 模拟和当前 HTTP 入口测试，未通过再次停止线上进程验证真实重启。
- **存储边界**：聊天消息保存在 Java 进程内；Redis 保存归属及实例编号。重启后本机记忆仍会丢失，实例校验只识别失效、不会恢复消息。尚无共享聊天记忆或完整历史归档。游客短期上下文不写入长期画像或向量库。
- **本机容量已实现并验收**：`auth.max-cached-conversations` 默认 100，使用独立许可限制本地跟踪的缓存会话；满额拒绝新会话并返回容量 503，已有空闲会话续聊复用原许可。调用结束保留缓存占用，空闲且已过期的记忆成功清理后归还；执行中和故障时保留并重试。12 项受控检查及 11 项真实 HTTP 检查通过，范围见[容量记录](m2-capacity-verification.md)。这不等于 Redis Key 总量或 JVM 字节上限。
- **长期画像管理与读取已实现**：MySQL `user_preference` 每个注册用户最多一条记录；本人 CRUD 接口通过 24 项 HTTP 与数据库检查。Agent 每轮读取当前画像作为默认口味，本轮明确需求优先；修改、删除后下一轮读取和跨用户隔离已有验证。
- **长期口味候选已实现**：新增 `proposeUserPreference`，校验输入、保留未修改字段并返回候选与状态，不直接持久化；已有分阶段工具及真实 HTTP 验证。同步响应和流式 done 均提供结构化候选，独立 PUT 确认保存及下一轮读取已验证。常点和预算习惯推断继续留待后续。
- **流式后端已实现**：模型增量通过 SSE 输出，真实与隔离检查见[SSE记录](m2-sse-verification.md)。SSE 连接超时 60 秒，流式模型每次上游请求超时配置为 60 秒，两者不是整条工具链的统一截止时间。超时或断连只关闭输出，模型或工具结束后才释放会话计数和许可；未收到 done 时回复不完整，不等于订单未创建，不自动重放请求。尚未提供即时取消上游任务或断点续传。
- **前端已接入**：fetch POST 消费 SSE，提供连续聊天、新对话、停止接收、真实报价确认与回执、报价编辑、订单核实、口味候选保存及清除确认。明确确认按钮透传真实草稿编号，不放宽后端校验；前端持久单元与订单核实浏览器回归、真实多轮点餐分别记录，见[前端记录](m2-frontend-verification.md)。刷新页面开启新对话，未实现聊天历史归档或列表。
- **首版收尾与后续范围**：核心功能及新版真实页面多轮点餐、明确下单、画像确认保存、新会话读取和明确清除均已验收。数量或搭配提醒不能擅自修改草稿或提交订单；候选数量偏差仍需优化，故障场景与 V1 回归另行推进，待办见 `docs/TODO.md`。

#### 4.2.1 注册用户长期画像首版

- 数据结构：`user_id` 为主键并关联 `user.user_id`；`spicy_level` 复用 `SpicyLevel`；`preference_text` 为最多 200 字的补充说明；记录 `created_at`、`updated_at`。完整 SQL 见[数据库建表语句](智能点餐系统数据库建表语句.md#m2-用户长期画像新表-sql)。
- 未设置与明确偏好分开：辣度 `NULL` 表示未知或已清空，`none` 表示明确偏好不辣；不能给所有新用户默认设置为不辣。
- 身份由后端有效 token 确定，游客不保存画像；不信任模型或请求体自行指定的用户 ID。
- 已提供 `GET /users/me/preference`、`PUT /users/me/preference`、`DELETE /users/me/preference`，均从有效 token 取得用户编号；无记录查询成功返回空数据。PUT 为整份替换，省略或传 `null` 会清空字段，重复删除允许成功。
- 普通长期口味作为推荐缺省条件，本轮用户明确要求优先；首版不持久化本轮人数、整单预算或完整聊天消息。
- 聊天中 LLM 可以提取候选偏好，由用户确认后通过可信保存操作提交；仅凭模型输出“用户已确认”不能触发持久化。
- 当前候选工具以 `SUCCESS`、`INVALID_ARGUMENTS`、`LOGIN_REQUIRED` 和候选数据返回处理结果；`SUCCESS` 仅表示候选已生成。未传入的候选字段保留原值，补充说明传入更新后的完整文本，由用户在保存前核对。
- 聊天 HTTP 响应通过 `proposalToolResult` 返回真实候选工具结果；普通聊天为空，失败结果也会覆盖本轮较早的成功候选。前端核对成功状态并展示完整候选，用户明确确认后调用独立画像 PUT，不能从模型文本解析持久化事实。初次界面阶段使用隔离服务，后续已通过真实页面确认保存、新会话读取、取消清除及明确清除，MySQL 核对与清理见[收尾记录](m2-closeout-verification.md)。
- 菜品反馈独立保存并已参与本人候选重排，不自动覆盖明确设置的画像。当前每次评分新增记录，同一次评价修改与再次用餐的区分尚未实现。

#### 4.2.2 语音输入与回复朗读首版

- 语音采用独立 HTTP 接口接入现有聊天，不增加新的 Agent 工具：`POST /speech/recognize` 接收 multipart 字段 `audio`，`POST /speech/synthesize` 接收 JSON 字段 `text`；均校验登录令牌。
- 识别模型为 `qwen3-asr-flash`。浏览器支持时使用 WebM/Opus 或 Ogg，首版限制60秒、5MiB；识别文字进入可编辑输入框，由用户手动发送。原文在识别期间变化时保留候选，超长不静默截断。
- 朗读模型为 `cosyvoice-v3-flash`，音色为 `longanhuan`，使用温和客服风格指令。完成回复后由用户点击生成，音频在当前页面保存供停止与重播；开始录音时停止朗读或取消等待。模型、音色和 API Key 由后端管理。
- 报价与订单朗读优先使用后端结构化摘要；清理 Markdown、内部 UUID 与 URL。明确拒绝、待核实与核实成功的朗读随可靠状态更新，不能朗读模型误报的下单成功。
- 语音输入已通过录音/上传与隔离浏览器检查，以及真实浏览器 WebM 的云端识别。真人麦克风完整页面链路待单独确认。朗读已由用户真实联调，菜名、金额、份数基本读准，声音与语速舒适；首播等待时间尚待分阶段计时优化。验证来源见[语音记录](m2-speech-verification.md)。

### 4.3 M3 · 运营助手（后续扩展，尚未开始）

- 定时根据天气和历史销量生成今日套餐、备货建议，由商户审核后使用。
- 真实库存预警依赖库存、原料与菜品关系及消耗记录，须先补齐数据模型；只有销量数据时不宣称能提供真实库存预警。
- 首阶段只生成建议，不自动上架、采购或修改订单。

### 4.4 M4 · 多 Agent 与场景扩展（可选、远期）

- 总控 Agent 与推荐、客服、库存等专家 Agent 协作，是否拆分由实际复杂度决定。
- 语音输入与按需朗读已作为 M2 后续体验改进单独实施、分别验收；语音直接下单、实时语音对话、菜单图像识别等扩展仍需另行定义需求。

## 5. M1/M2 明确不做的内容

- 真实支付，维持 `pending` / `paid` / `cancelled` 基础模型；下单成功不等于支付或制作完成。
- M1 不增加短信验证码登录，沿用 V1 手机号识别；token 校验不代表已验证手机号持有者，登录升级另行定义。
- 人脸识别、OCR、剩菜图像识别。
- 微服务拆分、多商户隔离、模型训练和复杂 RAG 微调。
- 自动采购、自动运营写操作和多 Agent 编排。

## 6. 核心验收场景（M1）

### 场景一：自然语言点餐闭环

用户提出“不辣、4 人、预算 200”，Agent 根据需求获取候选菜品，提出搭配和份数，调用 `draftOrder` 展示真实报价。用户明确确认并提交该 `confirmedDraftId` 后，`confirmOrder` 返回正式订单。

验收关注实际菜品、份数、预算、确认和订单结果，不限定工具顺序。没有可靠数据支持的忌口结论须说明限制。跨请求确认明确携带草稿编号；M2 已接入短期上下文，真实多轮点餐与报价调整的分阶段结果见[收尾记录](m2-closeout-verification.md)。

### 场景二：预算硬约束

候选列表不作为套餐报价。验证用户预算准确传入草稿，后端按单价乘份数计算总额；总额等于预算时允许确认，超过预算时拒绝首次提交。模型省略、提高预算或自行宣称满足预算不能通过验收。用户明确调整预算后须重新试算并确认。

### 场景三：人工确认闸门与草稿变化

- 生成草稿后，正式订单主表和明细无新增记录，允许存在 Redis 临时草稿。
- 没有确认字段、编号不匹配或仅要求“推荐完直接下单”时，不创建订单。
- 草稿过期、超预算、菜品下架或价格变化时，拒绝首次提交并要求重新试算、确认。
- 修改菜品、数量或预算后展示新草稿，不在同一轮自动提交新报价。

### 场景四：身份透传与数据隔离

- 注册用户身份来自有效 token，草稿和订单关联正确用户；游客订单不关联注册用户。
- 用户 A 不能确认用户 B 的草稿或读取其已有订单；两个游客 Session 同样互相隔离。
- Agent 历史订单工具仅允许查询本人，游客和越权请求被拒绝。工具签名不含用户编号，身份只来自后端调用上下文，模型无法指定他人。注册用户个性化推荐使用可信身份，不继续按游客上下文调用。
- 个性化推荐的身份透传和本人评分重排已通过真实对照，游客不受注册用户历史评分影响；历史订单工具已接入，真实 HTTP 验证覆盖本人最近 5 单查询、游客拒绝、越权拒绝及无订单如实提示，状态由模型转述为中文。

### 场景五：重复确认与并发提交

同一草稿连续确认返回相同订单编号。并发确认只产生一笔主订单和一套明细。验证实际数据库存在 `draft_id` 唯一约束，不能仅以捕获重复键异常作为证明。已有订单重试读取仍需校验归属，即使临时草稿已过期，也不重新创建订单。

### 场景六：工具与 LLM 失败降级

验证 LLM 超时、天气失败、Redis 草稿读写失败和身份服务不可用时的提示及限制。用户仍可使用不受故障影响的 V1 功能。额外验证“订单已提交、最终模型回复失败”：按草稿恢复订单结果，不重复下单。

### 场景七：V1 既有接口不受影响

V1 用户端菜单、推荐、手动下单、历史查询及商户接口在 V2 新增后仍正常。注册用户和游客均覆盖；新增订单草稿字段不影响原手动下单。

## 7. M1 完成标准

1. `/agent/chat` 完成候选推荐、真实草稿试算、明确确认和正式下单闭环。
2. Agent 创建正式订单经过后端确认闸门，模型不能绕过身份、预算、报价及菜品状态校验。
3. 注册用户和游客的草稿及订单归属正确；历史订单工具、菜单分类筛选、个性化推荐和独立天气工具均已接入并完成对应验收。推荐内部天气查询不等于独立工具已实现。
4. 重复及并发确认最多创建一笔订单，数据库约束与回复失败后的恢复行为有验证记录。
5. 工具与 LLM 故障有可读降级，受保护操作不会因降级而越权，V1 可用路径不被 V2 故障阻断。
6. 工具说明、参数及结构化结果清晰，本地启动、数据库初始化、Agent 请求与确认流程有说明。
7. 主要正常、拒绝、故障、并发及 V1 回归场景有可重复测试记录；代码机制、编译通过与场景验收通过分别记录。
8. 能解释 `AiServices` 装配、工具执行循环、临时草稿、可信调用上下文、人工确认和重复提交保护的设计。
