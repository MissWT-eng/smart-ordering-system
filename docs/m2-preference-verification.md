# M2 长期口味画像与候选生成验证记录

更新日期：2026-10-20。

本记录覆盖本人画像接口、Agent 读取长期口味、推荐报价边界与待确认候选工具。会话生命周期的分阶段记录见[会话验证记录](m2-memory-verification.md)。各轮针对当时实现验收，临时测试程序已清理，不等同于持续集成或最新代码的完整业务回归。

## 当前实现范围

- `user_preference` 保存每个注册用户的辣度、补充口味及时间字段；用户编号为主键，建表定义见[数据库文档](智能点餐系统数据库建表语句.md#m2-用户长期画像新表-sql)。
- 本人画像 GET、PUT、DELETE 根据有效 token 取得用户编号。PUT 是整份替换，省略或传 `null` 会清空字段；查询无画像返回空数据，重复删除可成功结束。
- 每轮聊天读取当前画像，只将两个口味字段通过 `@V("profileContext")` 传给模型；没有画像使用 `{}`，`null` 辣度表示未知，`none` 表示明确不辣。
- 本轮明确要求优先；画像修改、删除后下一条消息读取最新值，临时口味不自动写入数据库。
- `proposeUserPreference` 从可信调用上下文读取用户编号和原画像；模型仅填写候选口味参数。工具只返回待确认候选，不调用画像保存方法。
- 工具未传入的字段保留原值；补充说明是更新后的完整文本，由模型保留未被修改的原有偏好，并在保存前供用户核对。

## Agent 读取与推荐：画像行为通过，报价边界已回归

完成 15 项画像相关检查：游客及注册用户无画像、本人画像读取、新会话读取、双用户隔离、本轮微辣覆盖长期不辣、后续对话保留本轮需求、修改与删除画像后同会话读取、辣度未知、两个字段为空、无效 token、跨用户续聊拒绝，以及两次真实推荐。

真实推荐中的菜名和辣度对照在售菜品：长期不辣时返回不辣候选，本轮改为微辣后出现微辣候选；数据库中的长期画像保持原值。

初次真实推荐额外发现：用户要求不试算时，模型仍报告组合合计和预算结论。随后统一以下三处的规则：

1. `OrderingAgent` 的最终回复与草稿试算规则。
2. `RecommendationAssistant` 的推荐理由与 summary。
3. `recommendDish` 的工具描述与成功返回 nextAction。

回归使用原来的两个样例：

| 样例 | 观察结果 |
| --- | --- |
| 长期不辣、少油、喜欢菌菇；2 人、100 元；只推荐 2～3 道，不试算 | 返回 3 道不辣候选及真实单价，没有组合金额或整单预算结论 |
| 同会话本轮改成微辣；其余需求相同 | 微辣候选及单价正确，没有组合金额或整单预算结论；实际列出 4 道，未完全遵守 2～3 道要求 |

两轮均未新增 Redis 订单草稿或正式订单，长期画像未改写。报价边界的这两个样例通过，数量遵从性保留为待办；提示词改善不代表任意生成文本都具有程序级保证。

## 候选工具直接调用：17/17 通过

调用实际 `DishTools`，使用真实 Bean Validation；仅注入候选方法所需的 Validator，不调用模型、HTTP、MySQL 或 Redis。

1. 调用上下文为空，返回 `INVALID_ARGUMENTS`。
2. 缺少 ownerKey，返回 `INVALID_ARGUMENTS`。
3. ownerKey 为空白，返回 `INVALID_ARGUMENTS`。
4. 游客缺少注册用户编号，返回 `LOGIN_REQUIRED`。
5. 无旧画像且两个新字段均未提供，返回 `INVALID_ARGUMENTS`。
6. 有旧画像但未提供新字段，同样拒绝空候选。
7. 补充说明为空字符串时拒绝。
8. 补充说明全为空格、制表符、换行或全角空白时拒绝。
9. 即使提供辣度，也拒绝空白补充说明。
10. 201 字说明返回 `INVALID_ARGUMENTS`，包含对应字段的校验信息。
11. 200 字说明接受且不截断。
12. 无旧画像且只传辣度，成功返回候选，说明保持 null。
13. 无旧画像且只传说明，成功返回候选，辣度保持未知。
14. 只改辣度时保留原说明。
15. 只改说明时保留原辣度。
16. 两字段更新生效，原画像 DTO 不被修改。
17. 原辣度未知且本次未修改时，仍为 null，不自动设为 none。

成功结果包含非空候选；失败结果候选为空，状态、message 与 nextAction 有值。校验在候选组装后执行 `validator.validate(proposal)`，不校验裸字符串，也不把普通参数错误抛成模型异常。

## 候选真实 HTTP 行为：7/7 通过

使用已启动的 Spring Boot、真实模型、HTTP、MySQL 与 Redis，覆盖：

1. 注册用户没有画像时，能得到不辣、少油的待确认回复，数据库仍无画像。
2. 新增少油时，回复保留原来的不辣与喜欢菌菇。
3. 仅调整长期辣度为微辣，回复保留原有菌菇偏好。
4. 明确改成不吃菌菇时，候选回复反映替换意图。
5. 本轮临时微辣、2 人、100 元只用于用餐需求，不持久化。
6. 游客请求管理长期画像时，回复要求登录。
7. 无效 token 的聊天请求返回 HTTP/body 401。

每次聊天后按 SQL 核对画像及时间字段未被改写，正式订单数不变，也没有新增订单草稿。结束后恢复原画像，清理本轮 token 与 6 个 Redis 会话元数据；本机聊天记忆由既有空闲清理机制处理。

HTTP 部分验证的是回复行为与持久化边界，工具结构化结果由上述直接调用测试验证。当前聊天响应仅有 `conversationId` 与 `reply`，尚未返回独立的候选字段，也未完成从聊天候选到确认保存的整体流程。
