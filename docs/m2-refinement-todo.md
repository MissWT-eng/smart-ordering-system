### 1.1 后续补充中断后的订单结果核实

- [ ] 将本轮回复状态与订单业务状态分开；SSE 断连或模型最终回复失败，不直接把订单标为失败。
- [ ] 本轮实际发起过确认下单但未收到可靠回执时，展示“订单结果待核实”和查询入口。
- [ ] 通过可信身份和已确认的草稿编号查询真实订单，复用 `OrderService.findOrderByDraftId`；该查询只读取结果，不重新下单。
- [ ] 查到订单后显示真实回执及查看入口；未查到时显示“暂未查询到”，考虑提交仍在执行的情况。
- [ ] 普通推荐中断不展示订单结果待核实；不会自动重发确认请求。
- [ ] 订单已成功但最终回复失败时，从 MySQL 查询结果修正展示；聊天或其他缓存失效不能抹去真实订单事实。

验收重点：越权拒绝、已落库但最终回复中断仍可查回、暂未查到不误判失败；查询不重新下单。

## 2. 天气参与点餐

`queryWeather`、`WeatherInfoDTO`、`WeatherToolResult` 和天气提示词已接入。工具与推荐复用 `obtainCurrentWeather()`，外部请求集中在 `fetchCurrentWeather()`；Redis 按城市共享成功结果，默认缓存 300 秒。结果与限制见[天气验证记录](m2-weather-verification.md)。

- [x] 首版沿用门店所在城市，明确展示查询城市；当前配置为长春。
- [x] 结构化返回状态、城市、天气、温度、观测时间及获取时间；以真实服务结果为准。
- [x] 增加 Agent 天气工具，明确只问天气时不继续推荐、试算或下单；需要推荐时遵守用户限制。
- [x] 天气工具和推荐服务共用 Redis `weather:current:<cityId>`，命中不续期，不改写原观测及获取时间。
- [x] 缓存读写、损坏数据、天气接口异常分别处理；天气查询失败不缓存，推荐可以继续按已有需求执行。
- [x] 12 项缓存边界检查通过，包含真实 Redis 过期后重新查询、不同入口共享、时间字段与 TTL 保持规则。
- [x] 重启后通过 4 次真实 HTTP 请求验证两次独立会话查询、另一游客的推荐请求和 SSE 查询，业务表及草稿无新增。
- [ ] 任意城市、天气预报及上游观测时间的最大允许年龄另行设计；缓存 TTL 不等于观测数据年龄。
- [ ] 当前仍使用 V7；[官方 v7 文档](https://dev.qweather.com/docs/api/weather/weather-now-webapi-v7/)已标注将弃用，接口迁移与内部 DTO 分开推进。

## 6. 语音输入与自然、亲切的朗读

交互方向：用户点击录音 → 转成可编辑文字 → 检查后发送 → 使用现有 Agent 回复 → 按需点击朗读。

- [ ] 选择语音识别服务，确认音频格式、采样率、时长上限及 Java 接入方式。
- [ ] 设计录音、停止、取消、识别中、失败及无语音的页面状态；权限不可用时保留文字输入。
- [ ] 识别文字先进入输入框，允许修改后发送；语音识别结果不直接替代正式订单的明确确认。
- [ ] 自然亲切的声音作为明确目标，试听云端 TTS 候选，例如 CosyVoice 或豆包语音，再确定供应商与音色。
- [ ] 使用同一组点餐文案比较自然度、菜名/金额/份数读音与等待时间；供应商和音色目前未定。
- [ ] 朗读完成的回复或可靠报价摘要；处理 Markdown、编号、金额和停顿，避免播读草稿 UUID、内部字段或尚未完成的流式片段。
- [ ] 提供播放/停止控制，开始录音时处理正在播放的声音，避免把朗读再次识别为顾客输入。
- [ ] 凭证由后端管理，确认调用预算、长度限制、超时和失败提示。
- [ ] 验证权限拒绝、识别错误可修改、取消录音、不重复发送、播放切换及朗读内容与真实报价一致。
